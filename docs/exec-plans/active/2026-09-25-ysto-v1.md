# You Skipped The OP?! (ysto) v1

## Purpose
You Skipped The OP?! is a multiplayer anime music quiz that runs in the browser. Players join a lobby with a code and a name (no accounts), hear a random sample of an anime opening or ending, and pick the right anime from four options.

When this plan is done:
- A host creates a lobby and sets the sample length (10–30 s), the song pool (years, genres, OP/ED, formats, difficulty), the number of songs and the scoring rules. Friends join from desktop or phone, play a full game, see the final scoreboard, and can play again in the same lobby.
- Each player picks one of three themes (Shonen, Sakura, Tokyo Rain). Volume starts at 15%.
- The server makes every decision that affects the score. Nothing a client receives before the reveal identifies the song.
- The app runs as one Docker container on a VPS, with the audio library and the catalog mounted read-only.
- The public repo `github.com/xms61/ysto` holds code and docs only: no audio, metadata dumps, databases, `.env` files or keys. Automated checks enforce this.

To see it working, run `docker compose up -d` (or open the VPS's URL), create a lobby, join it from a phone with the code, and play a 5-song game.

The inputs live outside the repo, on the owner's machine. Their locations are set in `.env` (`YSTO_AUDIO_DIR`, and the file passed to `--from-dump`) and never written into committed files. They were surveyed on 2026-09-25.

| Source | Contents |
| :-- | :-- |
| Audio library | `.ogg` files in the AnimeThemes layout: `<year>/<Season>/<Basename>.ogg` from 2000 on, and `<decade>/` for the 60s–90s. Opus, 48 kHz stereo, about 315 kbps. File names follow AnimeThemes (`AoNoHako-OP1-NCBD1080.ogg`). |
| AnimeThemes dump | JSON fetched on 2026-09-19 from `api.animethemes.moe` by Anagroove's `scripts/sync_anime_metadata.ts`. It covers 4,940 anime and 14,447 themes (5,585 OP, 8,862 ED), with songs, artists, entries, videos and external IDs (MAL, AniList, Kitsu, aniDB, ANN, Anime-Planet). |
| Basename index | A basename → theme lookup that Anagroove builds from the dump. |

Findings:
- **Matching:** almost every file matches a theme by its basename. The scan lists the few that don't, which are duplicates (`.1` copies) and theatrical variants. Some themes have more than one file, such as a `-NCBD1080` variant.
- **Durations** (a random sample): mostly TV size, around 90 s. A few percent are under 45 s, and a few run past 2 minutes.
- **Tags:** the files carry only an encoder tag, with no title or artist tags.
- **Loudness:** a random sample measured about −16 LUFS integrated, so the AnimeThemes audio already looks normalized.
- **Metadata gaps:** the dump has one display name per anime (mostly romaji). It has no English or Japanese titles, genres, popularity, franchise grouping or cover art. 4,934 of the 4,940 anime have an AniList ID, and AniList supplies all of these.
- **Concentration:** Detective Conan has 79 themes, One Piece 73, Naruto Shippuuden 60 and Bleach 45. The 145 anime with 10 or more themes hold 2,320 themes (16%).
- **Shared songs:** 94 songs are credited to more than one anime, for example Date A Live and its OVA.
- **Formats and years:** TV 3,545, Movie 430, OVA 355, TV Short 331, ONA 198, Special 81. Years run from 1963 to 2026, and most anime are from 2010 or later.

## Game design
This section holds the v1 behavior, with the owner's answers from 2026-09-25 applied. M0 moves it into product specs.

### Game flow
Home → create a lobby, or join one with a code and a name → lobby (players, host settings, live pool size) → countdown → N rounds → results (podium and stats) → play again in the same lobby. A lobby with one player is solo play.

Every device plays the clip. A round runs like this:
```
server                                              clients
 | pick theme, sample offset, 4 options (kept here)  |
 | cut the clip with ffmpeg, issue a clip token      |
 |-- round:prepare { roundId, clipToken } ---------->| fetch and decode the clip
 |<- round:ready { roundId } ------------------------| barrier: everyone ready, or 8 s
 |-- round:start { startsAt, endsAt, options[4] } -->| play at startsAt, show the options
 |<- answer { roundId, option: 0-3 } ----------------| the first answer locks
 | close at endsAt, when everyone has answered, or   |
 |   at the first correct answer in First correct    |
 |-- round:reveal { correct, anime, song, scores } ->| about 7 s; the next clip is already cut
```
`startsAt` is about 1 s after the barrier, so every client has the message before the clip starts.

### Questions and options
- The sample plays for the whole answer window, which equals the sample length. There are four options and exactly one is right. The only text inputs in the app are the player name and the lobby code.
- The options are anime titles, shown in each player's title language: English, romaji or Japanese.
  - If any of the four has no title in that language, all four show romaji for that round, so a fallback never singles one out.
  - If two options have the same title, the year is added to both.
- Distractors never come from an anime credited with the same song. The same song means the same AnimeThemes song ID, or the same title and artists after normalization. The second test matters because a recap movie can reuse a TV opening under a separate song entry.
- Easy and Normal never use the answer's franchise. Their distractors come from the same popularity band as the answer, so the one famous title isn't a giveaway, and they match its format family (series, movie, OVA) when the pool allows.
- Hard fills the distractors from the answer's franchise first (other seasons, movies, spin-offs), so players have to know which season a song belongs to. The tight Hard match fills the rest.

  | Difficulty | Distractors |
  | :-- | :-- |
  | Easy | other franchises, popularity band ±25 percentile points |
  | Normal | other franchises, band ±15, era ±8 years |
  | Hard | the answer's franchise first, then band ±10, era ±3 years, at least one shared genre |

  If fewer than three candidates match, the band widens step by step.
- The option order is random each round and the same for every player in the lobby.

### Scoring
The host sets the scoring in the lobby, and presets bundle common combinations. The rules live in one pure module, `shared/scoring.ts`. Only the server runs it; clients display the results.

| Mode | A correct answer scores | The round ends |
| :-- | :-- | :-- |
| Speed (default) | `round(1000 × (1 − 0.5 × t / T))`: 500–1,000 points by response time `t` within the answer window `T` | at the deadline, or when everyone has answered |
| First correct | 1,000 for the first correct answer, 0 for later ones | at the first correct answer, or at the deadline |
| Flat | 1,000 | as in Speed |

| Modifier | Effect | Default |
| :-- | :-- | :-- |
| Streak bonus | +100 for each correct answer in a row after the first, up to +500 | on |
| Comeback | while a player is behind the leader, their streak bonus is doubled | off |
| Wrong-answer penalty | −250, or −500 in First correct | off; on in First correct |

- There are three presets: Classic (Speed with the streak bonus), Buzzer (First correct with the penalty) and Chill (Flat, no modifiers). The host can change any setting after picking one.
- Without a penalty, instant blind guessing would win about a quarter of the rounds in First correct. The −500 penalty makes that strategy lose points on average (0.25 × 1,000 − 0.75 × 500 = −125).
- Each player locks in one answer per round. Ties are ranked by the total response time of correct answers.
- The M9 playtest tunes the numbers and the comeback factor.

The interface is in English. Anime titles follow each player's title-language setting.

### Difficulty
- Each theme gets a difficulty score when the catalog is built. The score combines three things:
  - the anime's AniList popularity percentile
  - OP or ED (endings are less well known)
  - the sequence number (OP1 is better known than OP9)
- Each preset is a cut over the playable themes: Easy is the easiest 20%, Normal the easiest 50%, and Hard is all of them. Custom sets an anime popularity rank range.

### Song selection
- Songs are drawn in three steps (franchise, then anime, then theme) without replacement. That way long runners like Detective Conan, with 79 themes, don't crowd a game. An anime appears at most once per game.
- The lobby remembers the themes it has played, so "play again" avoids repeats until the pool runs out.
- The sample start is random on every play, uniform over `[3 s, duration − sample length − 5 s]`. Themes too short for that range are skipped for the game. The "intro" option starts at 0 s, which suits easy lobbies.
- Adult anime (AniList `isAdult`) are never in the pool.

### Lobbies and players
- **Codes** have 6 characters from a 31-character alphabet with no look-alikes (no 0/O or 1/I/L). That gives about 887 million codes, generated with `crypto.randomInt`. The lobby screen shows a join link (`/j/<code>`) and a QR code.
- **Names** are 1–20 characters after Unicode NFKC normalization and trimming. Control and format characters (zero-width, bidi overrides) are removed. Names are unique per lobby, ignoring case.
- **Lobby size and host:** up to 12 players. The creator is the host. When the host leaves, the player who has been connected longest takes over. The host can kick players, lock the lobby, skip a round whose clip sounds broken (a skipped round scores nothing), and change settings between games.
- **Late joins:** a player who joins during a game spectates until the next round starts, then plays from 0 points.
- **Reconnects:** a player who drops keeps their seat and score for 60 s.

### Themes
Each player picks a theme on their own device. The three themes are token sets (colors, type, texture, motion). They evoke the genres without any official artwork, logos, character names or fonts from One Piece, Naruto or Dragon Ball.
- **Shonen:** bold orange, black and yellow, with halftone and speed lines and heavy condensed type.
- **Sakura:** pastel pink, falling petals and soft rounded type.
- **Tokyo Rain:** dark navy with neon signs, rain on glass and glow.

All three meet WCAG AA contrast, respect `prefers-reduced-motion`, and use self-hosted fonts that cover Japanese.

### Audio in the browser
- Clips play through the Web Audio API: fetch, then `decodeAudioData`, then a `GainNode`. iOS Safari ignores `HTMLMediaElement.volume`, so a 15% default only works through a gain node. Web Audio can also schedule the start at `startsAt`.
- The Create or Join click unlocks the `AudioContext`, as browser autoplay rules require.
- Each client estimates its offset from the server clock with a ping/pong exchange, so all players hear the clip start at about the same moment.

## Architecture
### Stack
- Node 24, which runs TypeScript directly through type stripping, so the server has no build step. Express 5 and `ws` on the server.
- React 19, Vite, and Tailwind CSS v4 on the client, with the themes as CSS variables.
- SQLite through the built-in `node:sqlite`, so there is no native module to compile.
- ffmpeg as a system binary for cutting clips, and ffprobe for scanning the catalog.
- Tests: `node:test` for the server, shared code and scripts; Vitest with Testing Library for the client; Playwright end to end.
- npm, with `.nvmrc` pinned to 24.

### Code map (proposed)
- `shared/` holds the protocol message types and validators, the settings schema, defaults and presets, the scoring rules and the title-language helpers. It imports nothing from `server/` or `src/`.
- `server/` holds:
  - `main.ts` (wiring) and `config.ts` (the only code that reads env vars)
  - `http/` (headers, CORS, rate limits, routes) and `realtime/` (sockets, sessions, dispatch)
  - `game/` (lobby registry, state machine, question builder) and `clips/` (ffmpeg runner, token registry, route)
  - `catalog/` (loads SQLite into the in-memory index) and `shutdown.ts`
- `src/` holds the client: `screens/`, `components/`, `audio/`, `realtime/`, `themes/`, `prefs/`.
- `scripts/catalog/` holds the ingest and export steps. `scripts/check-docs.mjs` and `scripts/check-tracked-files.mjs` sit in `scripts/`.
- Tests: `tests/` for `node:test`, `src/**/*.test.tsx` for Vitest, and `e2e/` for Playwright.

ESLint's `no-restricted-imports` enforces the layer rules:
- `server/` and `src/` may import `shared/`, and `shared/` imports neither.
- `src/` never imports `server/`.
- Only `server/catalog/` and `scripts/catalog/` open SQLite.

### Game engine
`server/game/` is a pure state machine: `step(state, event, now, random) → { state, effects }`. The effects are "send to player", "broadcast", "set timer" and "prepare clip", and a thin shell runs them against real sockets and timers. Every rule (barrier, deadline, lock-in, scoring, host handover) can then be tested with a fake clock and a seeded random source.

### Runtime state
Lobbies, sessions, rounds and clip tokens live in memory in one process. Nothing about players is written to disk. A restart ends running games, and the shutdown hook tells clients first. One process serves dozens of lobbies. Serving more would need Redis and sticky sessions, which v1 doesn't need.

### Protocol
- Client → server: `hello { sessionToken }`, `round:ready`, `answer`, `time:ping`. Host only: `settings:update`, `game:start`, `game:again`, `round:skip`, `player:kick`, `lobby:lock`.
- Server → client: `lobby:state`, `round:prepare`, `round:start`, `round:answered` (who has answered, not what), `round:reveal`, `game:results`, `time:pong`, `error`, `server:closing`.

| HTTP route | Purpose |
| :-- | :-- |
| `POST /api/lobbies` | Create a lobby: `{ name }` → `{ code, playerId, sessionToken }` |
| `POST /api/lobbies/:code/players` | Join: `{ name }` → `{ playerId, sessionToken }` |
| `GET /api/clips/:token` | The round's clip. Needs `Authorization: Bearer <sessionToken>` from a player in that lobby. |
| `GET /covers/:file` | Cover art, referenced only in reveals |
| `GET /healthz`, `GET /readyz` | Liveness, and readiness: the catalog is loaded, the audio folder is readable, and ffmpeg is found |

### Ingest pipeline
`npm run catalog:build` runs these steps in order. Each step is also its own script, can resume, and is safe to rerun. Raw responses are cached in `YSTO_CACHE_DIR`, so a rerun doesn't fetch them again.
1. **`catalog:sync-animethemes`** pages through `api.animethemes.moe/anime`, including songs, artists, entries, videos, resources, series and synonyms. That's about 50 requests of 100 anime, one per second, with a User-Agent that names the repo. `--from-dump <file>` imports an existing dump instead.
2. **`catalog:scan-audio`** walks `YSTO_AUDIO_DIR` and matches file basenames to AnimeThemes videos. It reads durations with ffprobe (in parallel, cached by path, size and mtime), picks one primary file per theme, and lists unmatched files.
3. **`catalog:enrich-anilist`** sends batched GraphQL queries (`Page(perPage: 50) { media(id_in: …) }`), about 100 requests in total. They fetch titles (romaji, English, native), synonyms, genres, popularity, `isAdult`, the cover image and relations. The requests stay under AniList's rate limit and back off on 429, using `Retry-After`.
4. **`catalog:covers`** downloads each cover once into `covers/`.
5. **Assembly** writes a new `catalog.sqlite` next to the old one and renames it into place. It computes franchises, song identity keys, popularity percentiles and difficulty, fills `catalog_meta`, prints a report, and regenerates `docs/generated/catalog-schema.md`.
6. **`catalog:check`** is the gate. It requires:
   - at least 99% of files matched
   - a display title for every playable anime
   - popularity for at least 95% of anime
   - no playable adult anime
   - at least 50 themes for every genre offered in the settings
   - integrated loudness within −16 ± 2 LUFS on 200 random files

   If the loudness check fails, M1 adds a per-file gain, measured with ffmpeg's `ebur128` filter and applied when a clip is cut.
7. **`catalog:export`** (for the VPS) writes the primary file of every playable theme, re-encoded to 128 kbps Opus under the same relative paths, together with `catalog.sqlite` and `covers/`, into one folder ready for `rsync`.

**Franchises** come from the AnimeThemes `series` where it is set. Otherwise they are connected components over AniList relations of these types: prequel, sequel, parent, side story, spin-off, alternative, summary and compilation. The "character" and "other" relations are left out because they chain unrelated shows together. Hard mode now uses franchises to build its options, so wrong groupings show up directly in play. M1 therefore checks both sources against known franchises (Naruto, Gundam, Monogatari, Fate, Detective Conan) and reviews the 20 largest groups by hand.

**Refresh:** when the library changes (for example, a new season), rerun `catalog:build` and `catalog:export` on the machine that holds the full library, rsync the result, and restart the container.

## Security, anti-cheat and privacy
### Threat model
- **Assets:**
  - the answer of the current round, until the reveal
  - server CPU, which ffmpeg uses
  - the audio library, which is copyrighted and must not be downloadable in bulk
  - lobby availability
- **Actors:** a player with devtools or a modified client, anyone who finds the URL (lobby creation is open), a stranger guessing lobby codes, and a script flooding requests.
- **Accepted risk:** a player can use a song-recognition app or ask someone. There are no accounts and no global leaderboard, so cheating only affects the cheater's own lobby. Speed scoring and short samples blunt it.

### Score integrity and anti-cheat
1. The server owns every decision: the song, the sample offset, the options, the correct answer, the timer and the scores. Clients only render and send inputs.
2. Nothing before the reveal identifies the song:
   - The clip URL is an opaque random token.
   - No filename, theme, anime or song ID appears in any message or URL before the reveal.
   - The options are four strings in positions 0–3, with no database IDs.
   - The clip is re-encoded, so its bytes and length don't match the source file.
   - Metadata is stripped, and every clip is exactly the chosen length.
3. The options arrive with `round:start`, not with the prepare message, so nobody can research them while the clip loads.
4. Each player gets one answer per round. It is accepted between `startsAt` and `endsAt`, plus 300 ms of grace. Early, late and repeated answers are dropped.
5. The server measures response time: from `startsAt` to the answer's arrival, minus half the player's median round-trip time, capped at 150 ms. Clients never report times. In First correct, this adjusted time decides who was first, and arrival order breaks exact ties.
6. The reveal is sent only after the round has closed for everyone.
7. A leak test in M5 records every message sent before a reveal. It fails if any message contains the answer's titles, song, artists or IDs.

### Sessions without accounts
- Create and join are HTTPS POSTs that return a 256-bit random session token. The client keeps the token in `sessionStorage` (one seat per tab) and sends it as the first WebSocket message, never in a URL. There are no cookies, so there's nothing for CSRF to exploit.
- After `hello`, the player's identity is bound to the socket. The server never trusts a player ID in a message body.
- On every host action, the server checks that the sender is the lobby's host.
- Kicking a player ends their session, and that token can't rejoin the lobby.
- A lobby closes after 15 minutes with no connected player, and after 4 hours in any case.

### Input validation and limits
- There is one validator per message and request body, in `shared/protocol.ts`, written by hand like Anagroove's `server/validators.ts`. Settings are checked against the catalog's bounds (year range, genre list).
- WebSocket frames over 4 KiB are refused (`maxPayload`). JSON bodies over 4 KiB get a 413.
- Anyone who finds the URL can create lobbies, so these limits carry the abuse protection:
  - Per IP: 5 lobby creations per minute and at most 3 open lobbies; 30 joins per minute and 10 unknown codes per minute. Players in one home share an IP, so the connection cap per IP (30) stays above the lobby size.
  - Per socket: 20 messages per second. Repeated invalid messages close the socket with code 1008.
  - Global caps: `YSTO_MAX_LOBBIES`, `YSTO_MAX_GAMES`, `YSTO_MAX_PLAYERS` and the ffmpeg concurrency. Clips are cut only for running games with connected players, never for idle lobbies.
- React escapes all text, and the app never uses `dangerouslySetInnerHTML`.

### Media handling
- Each round's clip is cut on demand: `ffmpeg -ss <offset> -t <length> -i <file> -vn -map_metadata -1 -af afade…` encodes it to AAC at 128 kbps (about 480 KB for 30 s), with a 0.3 s fade in and a 0.5 s fade out. M3 picks the container (M4A, with MP3 as the fallback) after a decode test in Chromium, Firefox, WebKit and on a real iPhone.
- ffmpeg runs through `spawn` with an argument array (no shell), a 10 s timeout and a concurrency limit. If it fails, the round uses another theme (up to 3 tries), and the error is logged once.
- The client never sends a path or ID for audio. The server resolves `rel_path` against `YSTO_AUDIO_DIR` and refuses any path that ends up outside it, which guards against a bad catalog row.
- `GET /api/clips/:token` answers 404 for unknown, expired or other-lobby tokens. It never answers 403, so tokens can't be probed. Responses carry `Cache-Control: no-store` and no filename.
- A token lives from the prepare message until 10 s after the reveal ends. The next round's clip is cut during the current round.
- Covers are served from our own origin and referenced only in reveal messages.

### Secrets and third-party APIs
- The running server calls no third-party API and needs no secret. Metadata and covers come from the AnimeThemes and AniList APIs, which need no keys, and only the offline ingest scripts fetch them. Players' browsers talk only to our origin (no hotlinked images or fonts), so their IP addresses go nowhere else.
- `server/config.ts` is the only code that reads env vars. It validates them at startup and exits with a clear message on a bad value. `.env.example` lists every variable.
- If a secret is ever needed, it goes in `.env` locally, and in the host's environment or GitHub Actions secrets elsewhere. It is never logged or sent to clients, and it is added to the gitleaks rules. The VPS's SSH keys never go into the repo or into GitHub.
- The ingest scripts identify themselves with a User-Agent that names the repo, pace their requests, honor `Retry-After`, and cache responses. The About screen credits AnimeThemes and AniList. M1 checks their API terms, including any limits on non-commercial use.

### Keeping the public repo clean
Each layer backs up the others, so one mistake doesn't publish data:
1. `.gitignore` adds:
   - audio and video extensions (`ogg opus mp3 m4a aac flac wav webm mp4 mkv`)
   - `data/`, caches, covers, exports, dumps and SQLite files
   - `.env*` (except `.env.example`) and key files (`*.pem *.key *.p12 *.pfx id_*`)
2. `scripts/check-tracked-files.mjs` fails when a tracked or staged file has a forbidden extension, sits under a data path, or is over 1 MB (the lockfile is exempt). It runs in a pre-commit hook in `.githooks/` (enabled with `git config core.hooksPath .githooks`), in the pre-commit checklist and in CI.
3. gitleaks scans every push and PR in CI.
4. GitHub secret scanning and push protection are on for the repo. Both are free for public repos.
5. `.dockerignore` is an allowlist (`*`, then `!server/`, `!shared/`, `!src/`, …), so a new data folder can't enter the build context or the image. CI checks that the built image holds no audio or database files.
6. Code generates the test fixtures (sine tones from ffmpeg, synthetic catalog rows). Nothing is copied from the library.
7. Committed files contain no details of the owner's machine: no absolute paths, user names, machine names or folder layouts outside the repo. Docs and code refer to data locations by env var (`YSTO_AUDIO_DIR`), and the real values live only in `.env`.
   - The tracked-files check also scans text content for home-directory paths (Windows drive paths into the users folder, and macOS or Linux home folders) and fails on any match.
   - A gitleaks custom rule catches the same patterns in history.
   - Docs describe such paths in words, so the check never flags itself.

### Transport and headers
- HTTPS and `wss://` go through Caddy with HSTS. `YSTO_TRUST_PROXY` is set to its hop count.
- Every response gets a CSP of `default-src 'self'; img-src 'self' data:; media-src 'self' blob:; connect-src 'self'; font-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`. It also gets `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a `Permissions-Policy` and `X-Robots-Tag: noindex`. The end-to-end tests run with the production CSP in both browsers.
- WebSocket upgrades must come from the page's own origin or from `YSTO_ALLOWED_ORIGINS`.

### Privacy
There are no accounts, cookies, analytics or third-party requests. Names and tokens live in memory for as long as the lobby lasts. Logs never contain session tokens, clip tokens or player names. IP addresses stay in memory for rate limiting only.

### Legal note
The audio and the cover art are copyrighted, and this note is not legal advice. Lobby creation is open, so anyone who finds the URL can play clips. A few things keep the site low-profile: short clips, no downloads, no public lobby list, noindex, and attribution. If strangers start using it, a passphrase for creating lobbies is a small change (see [Beyond v1](#beyond-v1)). The themes use only original art and type.

## CI/CD, Docker and hosting
### CI
`.github/workflows/ci.yml` runs on every pull request and every push to `main`, and can also be started by hand. Its actions are pinned by commit SHA, and the workflow has `permissions: contents: read`.

| Job | Steps |
| :-- | :-- |
| `guard` | `check-tracked-files`, gitleaks |
| `docs` | the doc checker's tests, then the doc checks |
| `app` | `npm ci`, lint, typecheck, tests with coverage (lines and functions ≥ 85%, branches ≥ 75% on `shared/` and `server/`), web tests, build |
| `e2e` | install ffmpeg, generate the fixture catalog and sine-tone audio, build, then Playwright plays three rounds with two players in Chromium and WebKit |
| `docker` | build the image (no push), run it with the fixtures, wait for `/readyz`, check the image has no audio or database files, run a Trivy scan (fails on fixable high or critical issues) |

The repo also gets CodeQL default setup, plus Dependabot for npm, GitHub Actions and the Docker base image (weekly, grouped).

### Release and deploy
- `release.yml` is started by hand, like Anagroove's. It takes a version as input, then:
  1. reruns the CI jobs
  2. builds the image for amd64 and arm64 (ARM VPS plans are often cheaper)
  3. pushes `ghcr.io/xms61/ysto:<version>` and `:latest` with SBOM and provenance attestations
  4. tags `v<version>`
  5. creates a GitHub release from the CHANGELOG entry
- Deploys are pull-based: over SSH, the owner runs `docker compose pull && docker compose up -d` on the VPS. GitHub holds no deploy credentials, and there is no self-hosted runner, so pull requests from forks of the public repo can never reach the server.
- The image is public, and it holds no audio, catalog or covers.

### Docker
- The `Dockerfile` has three stages: dependencies, the Vite build (run on the build platform), and the runtime. The runtime is `node:24-alpine`, pinned by digest, with `ffmpeg` and `tini` from Alpine packages. It holds only production dependencies plus `server/`, `shared/` and `dist/`, runs as the non-root `node` user, and has a `HEALTHCHECK` on `/healthz`.
- `docker-compose.yml`:
```yaml
services:
  ysto:
    image: ghcr.io/xms61/ysto:latest
    restart: unless-stopped
    env_file: .env
    ports: ["127.0.0.1:3000:3000"]        # only Caddy on the same host reaches it
    volumes:
      - ${YSTO_AUDIO_HOST_DIR}:/data/audio:ro
      - ./data/catalog:/data/catalog:ro
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    mem_limit: 1g
    pids_limit: 256
    logging:
      driver: json-file
      options: { max-size: 10m, max-file: "3" }
```
- An `ingest` compose profile runs `npm run catalog:build` in the same image, with the catalog folder writable and network access for the APIs.
- For local development, Docker Desktop mounts the library folder read-only. The game reads one file per round, which bind mounts handle easily.

### VPS
The game runs on a rented VPS for friends. Anyone who has the URL can create a lobby.
- **Size:** 2–4 vCPUs, 4 GB of RAM, and disk for the library, or an attached volume. M3 measures the CPU cost of a clip, which confirms the size.
- **Library upload:** `npm run catalog:export` re-encodes the library at 128 kbps, which shrinks it to about 40% of its size. `rsync` sends the export folder to the VPS, and later runs send only changes. The catalog is built on the machine that holds the full library. Clips are re-encoded to 128 kbps AAC anyway, so a 128 kbps Opus source costs little quality.
- **Caddy** is the only service on the public ports (80 and 443). It gets certificates from Let's Encrypt, sets HSTS and proxies WebSockets.
- **Firewall:** only 22, 80 and 443 are open. Docker publishes ports past ufw rules, so the app binds to 127.0.0.1 (see the compose file) and only Caddy reaches it.
- **SSH** accepts keys only, root login is off, and security updates install unattended.
- **Search engines:** `robots.txt` disallows everything and every response carries `noindex`, so the site stays out of search results. There is no public lobby list.
