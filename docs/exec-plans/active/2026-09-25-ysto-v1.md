# You Skipped The OP?! (ysto) v1

## Purpose
You Skipped The OP?! is a multiplayer anime music quiz that runs in the browser. Players join a lobby with a code and a name (no accounts), hear a random sample of an anime opening or ending, and pick the right anime from four options.

When this plan is done:
- A host creates a lobby and sets the sample length (10–30 s), the song pool (years, genres, OP/ED, formats, difficulty), the number of songs and the scoring rules. Friends join from desktop or phone, play a full game, see the final scoreboard, and can play again in the same lobby.
- Each player picks one of three themes (Shonen, Sakura, Tokyo Rain). Volume starts at 15%.
- The server makes every decision that affects the score. Nothing a client receives before the reveal identifies the song.
- The app runs as one Docker container on a VPS, with the audio library and the catalog mounted read-only.
- The public repo `github.com/xms61/ysto` holds code and docs only: no audio, metadata dumps, databases, `.env` files or keys. Automated checks enforce this.

To see it working, run `docker compose up -d` (or open the VPS's URL), create a lobby, join it from a phone with the code, and play a 5-song game.

## Context
This work follows the repo's doc map ([AGENTS.md](../../../AGENTS.md)), the [release process](../../../.github/RELEASE_PROCESS.md), the [knowledge base rules](../../KNOWLEDGE_BASE.md), the [code style](../../CODE_STYLE.md), the [testing rules](../../TESTING.md) and the [plans guide](../../PLANS.md).

The inputs are the owner's audio library and the AnimeThemes metadata. What a survey of them found on 2026-09-25 is in the [catalog design doc](../../design-docs/catalog.md). Their locations live in `.env` only, never in committed files.

The same author wrote Anagroove, a music crossword game, on the same stack. These patterns are worth porting (copied and adapted, not imported):
- WebSocket rooms with resume tokens, heartbeats and failed-join limits (its `server/MULTIPLAYER_WS.md`)
- the security middleware for proxy trust, CSP and CORS (`server/API_SECURITY.md`)
- `server/validators.ts` and `server/shutdown.ts`
- the manual release workflow, with actions pinned by SHA

Anagroove's co-op mode sends answers to clients before the game ends. YSTO's design avoids that.

## Plan
Each milestone is one or more PRs on `feat/…` branches, each with a version bump, a CHANGELOG entry and updated docs ([release process](../../../.github/RELEASE_PROCESS.md)). A milestone is done when its "Done when" line holds.

### M0 Repository and guardrails (0.1.x)
- Run `git init` here, check `git status`, and stage explicit paths. The first commit holds the template and this plan. It is the one direct push, and it creates `main` on the new public repo `xms61/ysto`. Everything after goes through PRs.
- Before the first commit, scan every file to be committed for local paths and machine details, including this plan. The first commit happens before the guards exist, so this one check is done by hand.
- Repo settings: turn on secret scanning, push protection and Dependabot alerts. Add a ruleset on `main` (PR required, CI checks required, no force pushes) and CodeQL default setup.
- Fill in the template: AGENTS.md (the name, the commands, the always-rules), README, CHANGELOG, ARCHITECTURE.md, and the CI paragraph in RELEASE_PROCESS.md.
- Guards: the `.gitignore` additions, the allowlist `.dockerignore`, `scripts/check-tracked-files.mjs` with its local-path scan and tests, the pre-commit hook, gitleaks with the local-path rule, the `guard` job, and CI on every PR and push.
- Scaffold: `package.json`, the tsconfigs, ESLint with the layer rules, Prettier, a Vite + React + Tailwind page, an Express server with `/healthz`, and `node:test`, Vitest and Playwright wired into `npm run test:ci`.
- Docs: move the design from this plan into design docs and product specs, and bring the topic docs from stub to draft.

Done when: CI passes on the first PR, and test PRs that add an `.ogg` file, a fake key or a local home-directory path each fail the `guard` job, and `git ls-files` lists only code and docs.

### M1 Catalog (0.2.0)
- Write the ingest scripts from the [catalog design doc](../../design-docs/catalog.md), with caching, resume and strict flag parsing. Add `catalog:check` and the generated schema doc.
- Add the ESLint rule that only `server/catalog/` and `scripts/catalog/` open SQLite.
- Test on small fixtures written in test code (AnimeThemes and AniList JSON) and on tones generated with ffmpeg. The build gives the same output for the same inputs.

Done when: `npm run catalog:build` over the real library passes `catalog:check` (at least 99% of the files matched, a title for every playable anime, popularity for at least 95% of anime, no playable adult anime), the 20 largest franchise groups have been reviewed, and nothing under `data/` is tracked.

### M2 Question engine (0.3.0)
- `server/game/questions.ts` builds the pool from the settings, draws songs, picks sample offsets and distractors, and counts the pool size for the lobby ([questions](../../product-specs/questions.md)).
- Write `shared/scoring.ts` with the modes, modifiers and presets ([scoring](../../product-specs/scoring.md)).

Done when: the acceptance criteria of both specs hold, through tests over 10,000 seeded questions per difficulty and the scoring table of cases.

### M3 Clip service (0.4.0)
- Build the ffmpeg runner (argument array, timeout, concurrency limit) and a token registry with expiry. Add `GET /api/clips/:token` with the session check, and cut clips one round ahead ([audio clips](../../design-docs/audio-clips.md)).
- Run the browser decode test that settles the clip format.

Done when:
- tests show clips within 50 ms of the set length, and no tags in the output (checked with ffprobe)
- unknown, expired and other-lobby tokens get a 404
- a failed cut moves the round to another theme
- a 30 s clip takes under 500 ms to cut at the 95th percentile on the host

### M4 Lobbies and realtime (0.5.0)
- Build lobby create and join, `hello` and session binding, the 60 s reconnect grace, and heartbeats.
- Add host rights and handover, kick, lock and skip, and settings updates.
- Add the rate limits and caps, the security headers, lobby expiry, and graceful shutdown ([SECURITY.md](../../SECURITY.md)).

Done when: tests with several in-process WebSocket clients cover join, leave, reconnect, host handover and kick. Guessing unknown codes is throttled, the per-IP open-lobby cap holds, and oversized or malformed frames are refused.

### M5 Game loop (0.6.0)
- Build the state machine and its shell: the ready barrier with its timeout, the scheduled start, lock-in, the deadline and early end, the reveal, the results, play again, and spectators joining at the next round ([game flow](../../product-specs/game-flow.md)).

Done when:
- a fake-clock test plays a full game with 8 players in each scoring mode
- early, late and repeated answers are dropped
- scores match the scoring table
- the leak test from the [anti-cheat design](../../design-docs/anti-cheat.md) passes

### M6 Web client (0.7.0)
- Build the screens, mobile first:
  - home: create or join
  - lobby: players, host settings with the scoring presets, pool count, link and QR code
  - round: 4 options on keys 1–4, clip progress, timer
  - reveal and results
- Build the audio engine: Web Audio, the 15% default, unlocking on the first tap, and the scheduled start using the clock offset.
- Add player preferences (volume, theme, title language) and reconnect handling.

Done when:
- Playwright plays a three-round game with two browser contexts, in Chromium and in WebKit, against the fixture catalog
- Vitest covers the audio engine and the realtime client
- a real phone plays a game at 15% volume

### M7 Themes and polish (0.8.0)
- Build the three themes as token sets, plus a theme switcher ([DESIGN.md](../../DESIGN.md)).
- Add motion, with reduced-motion fallbacks.
- Show right and wrong answers with an icon and text, not color alone.
- Do a pass over the UI copy. For example, the reveal after a missed OP can say "You skipped the OP?!".

Done when: screenshots of every screen in every theme have been reviewed, axe (run in Playwright) reports no serious or critical issues, and contrast meets AA.

### M8 Docker, VPS and release (0.9.0)
- Decide the domain, the VPS provider and its CPU architecture (Q11).
- Write the Dockerfile, the compose file with its ingest profile, the Caddy config, `catalog:export`, `release.yml` publishing to GHCR, and the `docker` CI job ([hosting and deploy](../../design-docs/hosting-and-deploy.md)).
- Write a deploy runbook (`docs/DEPLOY.md`, linked from AGENTS.md) that covers the VPS setup, the library upload and the update routine.
- Bring the RELIABILITY and SECURITY docs to verified.

Done when:
- the VPS serves a full game over HTTPS from the uploaded library
- an external port scan shows only 22, 80 and 443
- CI's image check and Trivy pass
- a release run publishes the image

### M9 Hardening and 1.0 (1.0.0)
- Write a load script that runs simulated lobbies of 8 bots, against the targets in [RELIABILITY.md](../../RELIABILITY.md).
- Review security against SECURITY.md: headers, CSP, the WebSocket origin check, limits and token lifetimes.
- Playtest with friends, then tune scoring (including the comeback factor), difficulty cuts and timings.
- Run the doc-gardening pass before tagging 1.0 ([release process](../../../.github/RELEASE_PROCESS.md)).

Done when: the load targets are met, the review has no open high findings, playtest issues are fixed or tracked, the gardening pass's fix-ups are merged, and 1.0.0 is released.

## Beyond v1
Suggestions, roughly ordered by value for effort:
- A "Watch on AnimeThemes" link in the reveal. It's small and could join M6.
- A "flag this song" button in the reveal that logs a theme ID for catalog review.
- A passphrase for creating lobbies, if strangers start using the VPS.
- A daily challenge: the same 10 songs for everyone each day, with a result grid to share (Wordle style). It needs no accounts.
- AniList username import, which builds the pool from the anime on the players' lists (public API, no key needed).
- Adaptive difficulty from anonymous per-theme correct rates, kept in a separate, writable `stats.sqlite`.
- More modes:
  - guess the song title or the artist
  - "OP or ED?"
  - elimination with three lives
  - teams
- Jokers: 50:50 (removes two wrong options and halves the points), and "longer sample".
- Party mode: a TV plays the audio and phones are the controllers.
- Emote reactions during the reveal instead of chat, so there is nothing to moderate.
- A streamer mode that hides the lobby code, and a results image to share.
- A demographic filter (Shounen, Shoujo, Seinen, Josei, from AniList tags), which pairs well with the themes.
- UI translations.

## Decision log
Answered by the owner on 2026-09-25:
- 2026-09-25: Every device plays the clip, and the server starts it in sync (Q3), because groups play remotely as well as in one room. Rejected: host-screen-only party mode (moved to Beyond v1); both modes in v1.
- 2026-09-25: The game runs on a VPS, for friends (Q2). This adds the library export at 128 kbps, Caddy with HTTPS, a firewall setup that accounts for Docker's port publishing, and noindex. Rejected: a home machine; a public site for anyone.
- 2026-09-25: Anyone who has the URL can create lobbies. Per-IP and global caps protect the server instead of a passphrase, because the owner prefers no gate. Rejected: a passphrase for creating lobbies (kept in Beyond v1); a login in front of the site.
- 2026-09-25: Hard mode fills distractors from the answer's franchise first (Q1), so experts have to tell seasons apart. Easy and Normal never mix franchises. Rejected: never mixing franchises; options with OP/ED numbers.
- 2026-09-25: Scoring is a lobby setting (Q5), with three modes (Speed, First correct, Flat), three modifiers (streak, comeback, wrong-answer penalty) and presets, because the owner wants hosts to tune the feel. First correct gets a −500 wrong-answer penalty by default, because otherwise blind instant guessing wins about a quarter of the rounds. Rejected: one fixed scoring rule.
- 2026-09-25: CI runs on every PR and every push to `main` (Q8), because the repo is public and the guards must see every change. Rejected: the template's manual-only trigger.
- 2026-09-25: The repo is created after the plan is approved, as the first step of M0 (Q4). Rejected: creating it now with docs only; private first.
- 2026-09-25: Each player picks their own theme on their device (Q6). Rejected: a lobby theme set by the host; a host default with overrides.
- 2026-09-25: Nothing pushed may reveal the owner's machine: no absolute paths, user names, OS or machine details. Data locations are env vars, and the real values stay in `.env`. The owner asked for this because the repo is public. The tracked-files check and a gitleaks rule enforce it from M0 on.
- 2026-09-25: Lobbies hold up to 12 players. Late joiners spectate until the next round, then play from 0 points (Q7).
- 2026-09-25: The interface is English only in v1 (Q9). Rejected: translations (kept in Beyond v1).
- 2026-09-25: Anime titles show in English by default, falling back to romaji. Each player can switch to romaji or Japanese in their settings (Q10).
- 2026-09-25: The domain, the VPS provider and its CPU architecture are decided in M8, once the app is ready (Q11). Until then, releases build for amd64 and arm64.
- 2026-09-25: The VPS gets the library re-encoded to 128 kbps Opus, about 40% of the original size (Q12), because clips are re-encoded to 128 kbps AAC anyway. Rejected: uploading the original files.
- 2026-09-25: The plan describes the audio library generically, without its file count or size (Q13), because the owner wants the public repo to reveal nothing about their machine or what is on it.

Proposed on 2026-09-25 and not questioned:
- 2026-09-25: The stack is Node 24 (TypeScript without a build step), Express 5, `ws`, React 19, Vite, Tailwind v4 and `node:sqlite`, because it matches Anagroove: its patterns and tooling carry over, and nothing needs native compilation. Rejected: Next.js (no server rendering is needed, and WebSockets fit it poorly); Socket.IO and Colyseus (`ws` plus a small state machine covers the need without a framework).
- 2026-09-25: The catalog is a SQLite file built offline and loaded into memory at startup, because AnimeThemes' roughly 14,500 themes fit in a few megabytes and selection becomes plain filtering that tests can set up in code. Rejected: PostgreSQL (a server to run and back up, for data that is rebuilt from its sources).
- 2026-09-25: Lobbies live in memory in one process, because they last minutes and there are no accounts. Rejected: Redis (only needed for several instances).
- 2026-09-25: Clips are cut per round with ffmpeg at a random offset, because every play must sample a new random part of the song. Rejected: pre-cut clips at fixed offsets (Anagroove's approach, which gives a small, repeating set of samples); sending the full file (leaks the whole song).
- 2026-09-25: Clips are re-encoded to AAC with metadata stripped (M3 confirms the container), because every current browser decodes AAC and re-encoding keeps the clip from matching the source file. Rejected: slices of the Ogg Opus source (not every Safari version plays Ogg).
- 2026-09-25: Playback uses Web Audio with a gain node, because iOS ignores `HTMLMediaElement.volume`, so the 15% default would not apply there, and because scheduled starts keep players in sync. Rejected: the `<audio>` element.
- 2026-09-25: The server is authoritative, and the game engine is a pure state machine, because anti-cheat needs every scoring decision on the server, and a pure core can be tested with a fake clock. Rejected: checking answers on the client.
- 2026-09-25: Songs are drawn by franchise, then anime, then theme, because long runners (Detective Conan with 79 themes, One Piece with 73) would otherwise fill games. Rejected: drawing uniformly over themes.
- 2026-09-25: On Easy and Normal, distractors come from the answer's popularity band, and any title-language fallback applies to all four options, because otherwise the option that stands out is the answer. Rejected: random distractors.
- 2026-09-25: The server makes no third-party calls at runtime, and covers are served from our own origin, because player IPs stay with us, the CSP can stay `'self'`, and games keep working when AniList is down. Rejected: hotlinking AniList images.
- 2026-09-25: Session tokens live in `sessionStorage` and are sent over the WebSocket, because each tab can then be its own player, and without cookies there is no CSRF surface. Rejected: cookies; `localStorage` (tabs would share one seat).
- 2026-09-25: Deploys pull images from GHCR over SSH, because a public repo's CI must hold no credentials for the server. Rejected: SSH deploys from Actions; a self-hosted runner.
- 2026-09-25: `.dockerignore` is an allowlist, because a denylist lets a new data folder into the image.
- 2026-09-25: Validators are written by hand, one per message, in `shared/protocol.ts`, as in Anagroove. Rejected: zod (a dependency for about 15 small payloads).

## Surprises
- 2026-09-25: The audio is already loudness-normalized: a random sample measured about −16 LUFS. The planned per-file normalization became a spot check in `catalog:check`.
- 2026-09-25: The files carry no title or artist tags, only the encoder tag, so tags can't leak answers. Clips strip metadata anyway.
- 2026-09-25: Several majors were newer than planned: TypeScript 7 (the native compiler), Vite 8, Vitest 5, ESLint 10, checkout and setup-node v7, gitleaks-action v3. typescript-eslint doesn't support TypeScript 7 yet, so the scaffold pins 6.0.x.
